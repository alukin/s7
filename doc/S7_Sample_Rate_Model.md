# S7 Sample Rate Model

Status: first increment implemented (section 7). Written to settle the open rate/`dt` questions raised while planning numerical-modeling validation tests, before any such test work proceeds.

## 1. The problem

`dt` (the discretization interval) has no formal status in S7 today:

- `s7::Schema` has no schema-wide `dt`/rate field.
- An integrator's `dt` is an ordinary element parameter (`ParameterSpec{name:"dt", type:"real", ...}` — no different in the metadata system from a `Gain`'s `factor`), independently settable per element, with nothing checking two integrators in the same schema agree.
- A `sample_rate` concept *does* already exist, but only at the network-stream boundary: `S7_Network_Wire_Protocol_v1.md`/`S7_Net_Element_Contract.md` give `NetSource`/`NetSink` a `sample_rate` parameter expressed as a **rational number**, `{numerator, denominator}` elements per second — derived from the diagram's `dt` (*"a graph steps once per model-time step... with a model-time step (`dt` in the diagram, seconds) every stream is uniformly sampled: `sample_rate` is `1/dt` in exact form"*). Nothing computes or checks an equivalent value for a purely local (non-networked) wire.
- Today's only cross-element consistency mechanism is Studio's UI: `.s7diagram`'s top-level `dt` is rewritten into every element's own `dt`/`sample_rate_hz` parameter by `MainWindow::updateSchemaDiscretizationParams`, a Qt-only convention with no core/compiler enforcement and no effect outside Studio's own editing session.

So nothing in S7 can answer "what is the sample rate at this wire" except by manually tracing `dt` parameters by hand — and nothing stops two connected elements from silently disagreeing.

## 2. Precedent in comparable systems

**GNU Radio** (a block/flowgraph signal-processing system closely analogous to S7) enforces rate consistency at the *ratio* level, not the absolute-Hz level. A rate-changing block (decimator, interpolator, rational resampler) declares a relative rate to the scheduler — for a rational resampler with interpolation `L` and decimation `M`, the output rate is `L/M` times the input rate, with `L`/`M` kept small and coprime for efficiency ([Rational Resampler](https://wiki.gnuradio.org/index.php/Rational_Resampler)). The scheduler uses this ratio for buffer bookkeeping; it does not independently verify that an absolute `samp_rate` variable used elsewhere in the flowgraph (e.g. to compute a filter's cutoff) actually matches — that remains the flowgraph author's responsibility, conventionally centralized in one shared variable in GNU Radio Companion. Separately, hardware source blocks (e.g. an uhd/USRP source) emit **stream tags** — `rx_time`, and in several releases `rx_rate`/`rx_freq` — carrying the actual, hardware-reported rate/time/frequency at the point they are set, which propagate downstream to any block that cares ([gr-uhd usrp_source header, 3.7.x](https://www.gnuradio.org/doc/doxygen-3.7.2/usrp__source_8h_source.html); the exact tag set has drifted across releases — [3.10.x's header](https://www.gnuradio.org/doc/doxygen/usrp__source_8h_source.html) documents only `rx_time` in that comment, unconfirmed whether `rx_rate` was dropped or just under-documented there). The durable idea, not the exact tag list, is what matters: a hardware source's actual rate is runtime-reported truth, separate from and potentially overriding a flowgraph's design-time assumption.

**Simulink** goes further toward exactly what was asked for here — *"know a rate of samples... on each wire."* Its **Sample Time Colors** display (Format menu) colors every block and line by its resolved sample time: black for continuous, magenta for constant, then a distinct color per successively slower discrete rate; a block whose contents mix rates (a subsystem, a Mux/Demux carrying signals of different rates) gets a distinct "hybrid" color instead of being forced into one. Sample times are a real, queryable, resolved property (`Simulink.BlockDiagram.getSampleTimes`), not a convention. Crossing between rates in multitasking execution requires an explicit **Rate Transition** block, with direction-dependent, specified behavior: a zero-order hold when moving from a faster task to a slower one, a unit delay when moving from a slower task to a faster one (protecting data integrity against task preemption). Simulink *can* insert these automatically (a model configuration option), which S7 should not copy — see section 4.

Sources: [Specify Sample Time](https://www.mathworks.com/help/simulink/ug/how-to-specify-the-sample-time.html), [RTE Rate Transition](https://opal-rt.atlassian.net/wiki/spaces/PRD/pages/144018223/RTE+Rate+Transition), [Convert Sample and Frame Rates Using Rate Conversion Blocks](https://www.mathworks.com/help/dsp/ug/convert-sample-and-frame-rates-in-simulink-using-rate-conversion-blocks.html).

## 3. Design: rate as an inferred port property, mirroring the existing type system

S7 already has exactly the right shaped mechanism for a different property — `SignalType` — and it should be extended, not duplicated, for rate:

- **`Rate`**: a rational number, `{numerator, denominator}` samples per second — reusing, verbatim, the representation the wire protocol already chose for stream descriptors (section 1), not inventing a second one and not using a float (a float would reintroduce exactly the drift/equality problems rational arithmetic was chosen to avoid at the network boundary).
- **`RateVariable`** (mirrors `TypeVariable` in `s7core/include/s7/type_inference.hpp`): a name, an optional pinned `Rate` (from a parameter, or from a hardware element's physically fixed rate), otherwise inferred from connections.
- **`PortRateRule`** (mirrors `PortTypeRule`'s `Fixed`/`Variable`/`ComponentOf`/`ComplexOf` kinds): `Fixed` (a literal rate — a hardware source/sink), `Variable` (this port shares the element's one rate variable — the default for nearly every existing element: `Gain`, `Adder`, `Multiply`, `Delay`, `PreviousValue`, `IirFilter`, `FirFilter`, the integrators, `Constant`, `AnalogOscillator` all have exactly one rate across every port, i.e. GNU Radio's "relative rate = 1"), and a new kind, `RatioOf` (this port's rate is the variable's rate times a declared rational ratio — what a rate-changing element uses).
- **`RateResolver::resolve(schema)`** (mirrors `TypeResolver::resolve`): a unification pass giving every port a resolved `Rate`. Connected ports must resolve equal **unless** an element between them declares a `RatioOf` relationship (a rate-changing element sits exactly there) — exactly as `S7_Net_Element_Contract.md` already states for type, generalized to rate: *"nothing resamples implicitly; use an explicit rate-changing element."* A variable left with no seed is a validation error ("rate undetermined"), not a silent default — unlike type inference's "defaults to F64" rule, because guessing a rate is far more dangerous than guessing a numeric type, and no one needs that silent behavior for this to still cover the common case (section 5). A conflict (two connected ports forced to different rates, no rate-changing element between them) is a validation error naming the element and port, exactly like a type conflict today.
- **Seeds**: a hardware I/O element pins its rate the way a fixed-type port pins its `SignalType` today; an optional schema-level `Rate` field (promoting `.s7diagram`'s Studio-only top-level `dt` into `s7::Schema` itself, where the resolver can actually see it) seeds every otherwise-unconstrained variable. This replaces Studio's `updateSchemaDiscretizationParams` UI rewrite with one real mechanism the compiler runs — shared by Studio and any headless tooling, instead of two hand-written copies that can drift (as flagged in `s7l2/docs/OPEN_PROBLEMS.md`).
- **The rate-changing element** (`Resample`, name not final) is the already-tracked `DEVELOPMENT_PLAN.md` Phase 5 item, now given a precise shape: it declares an input `Variable` rule and an output `RatioOf` rule (or vice versa), with Simulink's Rate Transition semantics as the behavioral template — direction-dependent (hold going to a slower rate, delay/buffer going to a faster one), not a single generic interpolation formula, and parametrized by an explicit rational ratio, never inferred from context.

## 4. Deliberate divergence from Simulink: no automatic insertion

Simulink can auto-insert Rate Transition blocks (*"Automatically handle rate transition for data transfer"*). S7 should not adopt this. It already has an established, stronger rule for the directly analogous type-system problem — `S7_Net_Element_Contract.md`: *"nothing converts implicitly (use `Convert` before a `NetSink` or after a `NetSource`)"* — and `AGENTS.md`'s own guardrails: *"prefer explicit errors around schema/type mismatches over silent coercion."* A rate mismatch between two connected ports should be a validation error naming the element, full stop; the rate-changing element must be placed explicitly by whoever builds the schema, never inserted silently on the model's behalf.

## 5. Clock domains: generalizing what already exists, not inventing a second concept

The wire protocol already has the right discipline for this, just scoped to the network boundary: three timestamp roles (`MODEL_TIME`, `SOURCE_TIME`, `PROCESSING_TIME`), each tied to a declared clock domain (`NODE_INFO.clock_domains`), with an explicit rule — *"Receivers MUST NOT directly compare timestamps from different domains unless configuration explicitly declares a conversion/synchronization relationship."* A hardware element's rate boundary is structurally the same situation as a network peer's clock boundary — its rate is tied to its own physical clock, generally not synchronized with the model's simulated time — so a rate-changing element crossing into/out of a hardware domain should carry (or be checkable against) a clock-domain declaration, rather than inventing a parallel "rate domain" concept distinct from the clock domains the protocol already has. `S7_Terminology.md` currently defines none of "sample rate," "clock domain," or "model time" despite the wire protocol using all three extensively — this should be fixed alongside whichever of this document's pieces get implemented, not left undefined.

## 6. Scoping: inference and validation now, execution and scheduling later

`S7_Architectural_Decisions.md` ADR-007 ("Connections Define Causality") already establishes the needed separation for exactly this kind of question: *"Connections define causality. Schedulers enforce causality. Schedulers do not create causality... execution strategy becomes replaceable; semantics remain independent of implementation."* Section 3's resolver is semantic/structural — what rate relationship exists at each port — and is fully specifiable without first solving how a genuinely multi-rate graph actually *executes*: whether `NodeRuntime::step()` runs at the fastest rate domain's pace and skips slower-domain elements on some steps, whether independently-clocked rate domains get their own schedulers closer to GNU Radio's per-block asynchronous model, or whether a hardware-rate element behaves like `NetSource`/`NetSink` with its own internal buffering thread decoupled from the local step loop. That execution question is real and hard, and is explicitly **out of scope** for this document — it belongs with `DEVELOPMENT_PLAN.md` Phase 5's existing "distributed scheduling and coherence domains" item, broadened to cover local multi-rate execution, not just the network case.

**The degenerate case needs none of that.** Every stage currently planned in `s7l2/docs/VISUAL_NUMERICAL_TESTS_PLAN.md` has no hardware elements and no rate-changing elements — so the resolver, run on any of those schemas, has exactly one rate variable for the whole connected graph, and `NodeRuntime::step()`'s existing single global tick is exactly correct once that is *confirmed*, not merely assumed. Section 3's design is therefore necessary and sufficient to unblock that work, without requiring the harder execution-model question to be answered first.

## 7. Status and what this changes

**First increment implemented (2026-10-14).** Section 3's resolver exists in `s7core`: `Rate` (`s7core/include/s7/rate.hpp`), `Element::declared_rate()` (overridden by `EulerIntegratorT`/`TrapezoidIntegratorT`/`AnalogOscillatorT`), `Schema::rate()`/`set_rate()` (the schema-level seed), and `RateResolver::resolve()` (`s7core/include/s7/rate_inference.hpp`), tested by `s7core_rate_inference_smoke`. It covers the degenerate case this document's section 6 already identified as necessary and sufficient for `VISUAL_NUMERICAL_TESTS_PLAN.md`: one rate per element, shared by every one of its ports — true of every element that exists today. The `PortRateRule::RatioOf` kind (an element with input/output ports at different, explicitly related rates — what the not-yet-existing rate-changing element needs) is not yet built; nothing needs it until that element exists. The resolver is also not yet wired into `Validator::validate()`/`Compiler::compile()` as a mandatory gate — doing so would newly fail every schema that has no rate-pinning element and no seed, which is most schemas today, so that wiring is a separate, deliberate follow-up (tracked in `s7l2/docs/OPEN_PROBLEMS.md` and `DEVELOPMENT_PLAN.md` Phase 1), not an oversight. It supersedes the ad hoc "propagate one `dt` value by hand" approach in `VISUAL_NUMERICAL_TESTS_PLAN.md` section 1.3 as the target design, and consolidates the dt-propagation-duplication and rate/resample entries already in `s7l2/docs/OPEN_PROBLEMS.md`.
